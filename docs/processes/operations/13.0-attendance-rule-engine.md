# 13.0 Attendance Rule Engine

*Reads Attendance Rules, evaluates each against the member population, and applies the configured outcomes. Derived from the System Design Specification §13.6. Where this document conflicts with the specification, the specification wins.*

---

## Responsibility

13.0 Attendance Rule Engine evaluates the administrator-configured Attendance Rules and applies their outcomes. It is the process that turns attendance facts into member status changes.

Attendance is a fact. The rule engine is the mechanism that interprets the fact over time and produces configured outcomes. The mechanism is fixed; the rules and their values are configured by the administrator.

**Source:** System Design Specification §13.6.

---

## Trigger

Two triggers:

- **Scheduled run.** The engine runs on a configured schedule.
- **Manual admin trigger.** An administrator may invoke the engine on demand.

The engine does not depend on any other process running first. It reads current attendance, current rules, and current member state, and applies what its rules say.

**Source:** System Design Specification §13.6.

## The footprint

| Direction | Store |
| --- | --- |
| Reads | D2 (AttendanceRule, AttendanceRuleScope), D3 (Branch.UsesAttendanceRegister, Event.UsesAttendanceRegister — effective scope), D4 (Member, MemberStatus), D5 (Readmission), D7 (AttendanceRecord), D10 (MemberStatus lookup), D11 (SystemSetting — the global register scope) |
| Writes | D4 (MemberStatusID when a SetStatus outcome fires), D5 (Readmission rows when readmission is recorded) |

**Never reads or writes:** D1, D6, D8, D9, D12. Never modifies AttendanceRecord. Never modifies any assignment. Never modifies fill status. Never invokes any process.

**Source:** System Design Specification §13.6.

## The Attendance Rule entity

An Attendance Rule is one row created by the administrator. It carries:

| Column | Meaning |
| --- | --- |
| AttendanceRuleID | Primary key |
| Name | Administrator-defined label |
| TriggerType | AbsenceDays, ReadmissionCount, or Manual |
| TriggerValue | The trigger's value. Days for AbsenceDays, count for ReadmissionCount. Unused for Manual. |
| OutcomeType | Notify, SetStatus, IncrementReadmissionCount, or NoOp |
| OutcomeStatusID | Foreign key to Member Status. Set only when OutcomeType = SetStatus. |
| Enabled | When false, the rule is not evaluated. |

The rule's scope is expressed through the Attendance Rule Scope join table. Multiple scope rows for one rule are ANDed, using the same criterion vocabulary as Duty Rules. A rule with no scope rows applies to every member.

**Source:** System Design Specification §4 (Attendance Rule, Attendance Rule Scope), §13.6.

---

## Trigger vocabulary

- **AbsenceDays.** The member has not attended any occurrence within the last N days. N is TriggerValue.
- **ReadmissionCount.** The member has accumulated N readmission events. N is TriggerValue.
- **Manual.** The rule fires only when an administrator invokes it. TriggerValue is unused.

**Source:** System Design Specification §13.6.

---

## Outcome vocabulary

- **Notify.** A notification is composed and sent through the configured channel. No status change.
- **SetStatus.** The member's MemberStatusID is set to the status named by OutcomeStatusID.
- **IncrementReadmissionCount.** The member's readmission count is incremented. In the current phase, readmission counts are derived from Readmission rows, which are recorded by an administrator. The outcome is a no-op until readmission recording is more fully specified.
- **NoOp.** The rule does nothing. Used to define a rule that is disabled without deleting it.

**Source:** System Design Specification §13.6.

---

## Evaluation order

For each enabled rule:

1. Resolve the rule's scope criteria. A member matches the rule only if every scope criterion matches.
2. Resolve the effective attendance register scope for the member's occurrences.
3. If the effective scope is off, skip the member for AbsenceDays triggers.
4. Evaluate the trigger. AbsenceDays compares the member's last attendance against the current date, against TriggerValue. ReadmissionCount compares the member's readmission count against TriggerValue. Manual fires only when the admin invokes the rule explicitly.
5. Apply the outcome.

The engine is idempotent. Running twice with unchanged data produces the same result.

**Source:** System Design Specification §13.6.

---

## The scope resolution

A member's effective attendance register scope is the most specific of the three scopes that applies:

- Event override, when the member's occurrence is event-sourced and the event carries an override.
- Branch override, when the member's occurrence is schedule-sourced at a branch that carries an override.
- Global default, when no override exists.

When the effective scope is off, the engine does not apply AbsenceDays rules to that member. This is what allows a branch that does not use the attendance register to be exempt from absence-driven status changes. A branch that does use the register is subject to them.

The two cases are expressed as separate rules. A rule scoped to one branch group may be absent-based; a rule scoped to a different group may not. The system does not decide which members are subject to absence rules. The administrator does, through the scopes of the rules.

**Source:** System Design Specification §9.6, §13.6.

## Interaction with other processes

- **6.0 Record Attendance** writes AttendanceRecord rows. 13.0 reads them.
- **5.0 Generate Assignment** reads AttendanceRecord only when a Branch-Attendance Recency criterion is present and the effective register scope is on. 13.0 does not feed 5.0 directly; both read the same store.
- **9.0 Dispatch Notification** is invoked by 13.0 when a Notify outcome fires. This is a new invocation edge. It is a fourth edge terminating at 9.0.
- **3.0 Manage Membership** may set member status directly. 13.0 also sets member status. Both write the same field.

**Source:** System Design Specification §16.

---

## Invariants

- Idempotent per run.
- Reads attendance facts, does not modify them.
- Writes only MemberStatusID and Readmission rows.
- Invokes only 9.0, and only when a Notify outcome fires.
- On no other invocation edge.
- Does not resolve the scope of any rule on its own initiative. It applies the scopes the administrator configured.
- Does not interpret any Member Status name or Attendance Rule name.
- Uses the same criterion vocabulary and evaluation as Duty Rules.

**Source:** System Design Specification §13.6, §16.

## Candidate access patterns

- **`AttendanceRule (Enabled)`** — natural access pattern for the enabled rule set.
- **`AttendanceRuleScope (AttendanceRuleID)`** — natural access pattern for resolving a rule's scope.
- **`AttendanceRecord (MemberID, Timestamp)`** — natural access pattern for the absence check.
- **`Readmission (MemberID, IsDeleted)`** — natural access pattern for the readmission count.

Physical forms are implementation-dependent.
