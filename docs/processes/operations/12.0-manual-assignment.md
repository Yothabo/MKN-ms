# 12.0 Create Manual Assignment

*Directly creates a Roster Assignment from an administrator's selection, bypassing 5.0's tiered candidate ranking while respecting Eligibility Flag criteria and the uniqueness constraint. Derived from the System Design Specification §17. Where this document conflicts with the specification, the specification wins.*

---

## Responsibility

12.0 Create Manual Assignment is the process by which an administrator directly creates a Roster Assignment. It is the operation referenced throughout the specification by `AssignmentSource = Manual` and `AssignedBy`.

It is the only process other than 5.0 that writes a new Roster Assignment row from scratch.

**Source:** System Design Specification §17.

---

## Trigger

Administrator action. No scheduled component.

**Source:** System Design Specification §17.1 (A1).

---

## The footprint

| Direction | Store |
| --- | --- |
| Reads | D4 (Member — the selected member), D3 (ServiceOccurrence — the target occurrence), D2 (DutyRule — Eligibility Flag tiers only), D6 (Eligibility — only when a DutyRule references Eligibility Flag), D7 (RosterAssignment — uniqueness check) |
| Writes | D7 (RosterAssignment insert only) |
| Invokes | 9.0 Dispatch Notification, only when the created row's AssignmentStatusID is NULL |

**Never reads or writes:** D1, D5, D9, D11, D12. Never modifies ServiceOccurrence. Never modifies ServiceOccurrenceDuty. Never modifies an existing RosterAssignment row.

**Source:** System Design Specification §17.4.

---

## Scope

Applies to any Service Occurrence — schedule-sourced or event-sourced. There is no restriction on which occurrences may receive a manual assignment.

No ordering dependency on 5.0. A manual assignment can be created whether or not 5.0 has already run against the occurrence.

**Source:** System Design Specification §17.1 (A2, A3).

---

## What is bypassed and what is not

### Bypassed

Manual assignment bypasses Duty Rule tiers whose CriteriaType is:

- Role
- Gender
- Age Range
- Tenure
- Membership Stage
- Branch-Attendance Recency

The administrator may select any member for any duty, including a member that would produce zero candidates under 5.0's automatic resolution. These criteria types express ranking and filtering preferences for the automatic engine; an admin exercising direct judgment is the decision-maker the engine's ranking exists to assist, not replace.

### Not bypassed

Manual assignment does **not** bypass a Duty Rule tier whose CriteriaType is **Eligibility Flag**.

If any configured tier for the duty references an Eligibility Flag, the selected member must hold a current, valid Eligibility grant for that duty — regardless of assignment source.

Eligibility Flag is the one place a locked distinction from earlier in the specification must be protected. It represents a separate, accountable determination made by a specific authority, built with its own grant/revoke audit trail specifically so a sensitive determination would never be reduced to a bypassable preference. Letting manual assignment route around it would quietly undo that protection. Everywhere else, admin discretion is real discretion; here, it is not — because the discretion being protected belongs to whoever grants the Eligibility, not to whoever is creating the roster assignment.

**Source:** System Design Specification §17.1 (B1, B2).

---

## What is not enforced

- **Slot capacity.** Manual assignment does not enforce the effective required slot count (RequiredSlotCount, as adjusted by Service Occurrence Duty overrides). An admin may create a manual assignment even when the duty is already at or above its configured count.
- **Per-occurrence availability.** Manual assignment does not enforce 5.0's rule that a member may not hold a non-terminal assignment on the occurrence at all. An admin may knowingly assign the same member to a second duty on the same occurrence.

Both are the double-duty / shortage-exception cases that the specification has deliberately established as admin decision points, not automatic ones.

**Source:** System Design Specification §17.1 (B3, B4).

---

## What is enforced

**Uniqueness.** The (MemberID, DutyID, OccurrenceID) uniqueness constraint applies. A manual assignment duplicating an existing combination is rejected.

This is a data-integrity rule, not a business rule. It protects against a genuine error state (the same person recorded twice for the same slot), not a judgment call — nothing about admin discretion should touch it.

**Source:** System Design Specification §17.1 (B5).

---

## Eligibility Flag resolution

For each Duty Rule row attached to the target duty where CriteriaType = Eligibility Flag, 12.0 resolves the applicable Eligibility row using the same rule 5.0 uses (§10.1.4): the row with the latest GrantedDate whose RevokedDate is null, tiebroken by the greatest EligibilityID.

If no such row exists, or the resolved row's RevokedDate is set, the manual assignment is rejected.

If the duty has no Duty Rule row with CriteriaType = Eligibility Flag, there is nothing to check, and 12.0 proceeds without consulting Eligibility at all.

**Source:** System Design Specification §17.3.2.

## Status and lifecycle

### Admin-selected status

The administrator explicitly sets `AssignmentStatusID` at creation, to either a specific admin-defined status or `NULL`.

- An admin assigning someone who has already verbally agreed can mark the assignment **confirmed** immediately.
- An admin who still wants the normal response flow leaves it **NULL** and lets 7.0 take over, identically to an automatic assignment.

### Notification behavior

9.0 Dispatch Notification is invoked **only when the created assignment's `AssignmentStatusID` is NULL** at creation. A notification asking someone to confirm something the admin already recorded as confirmed would be actively confusing.

This mirrors exactly how 5.0 and 7.0 already invoke 9.0 — only when a response is genuinely being requested.

### Downstream lifecycle

Once created with `AssignmentStatusID = NULL`, a manual assignment is indistinguishable from an automatic one to every downstream process. 7.0 owns its lifecycle exactly as it would for a 5.0-created row.

`AssignmentSource = Manual` and `AssignedBy` remain as **permanent provenance**, but do not alter 7.0's or 10.0's behavior in any way. Provenance is a historical fact worth keeping; it is not a second lifecycle system.

A manual assignment created with a non-null `AssignmentStatusID` is never picked up by 7.0's timeout sweep. Timeout is measured from `CreatedAt` for assignments awaiting a response; an assignment that was never awaiting one has nothing to time out.

**Source:** System Design Specification §17.1 (C1–C4).

---

## Replacement interaction

If a manual assignment later enters 7.0's lifecycle (because it started NULL) and is declined or times out, 7.0's existing re-resolution logic applies without modification. The replacement it creates is `AssignmentSource = Automatic` — the same as any other 7.0-created replacement.

**Source:** System Design Specification §17.1 (D1).

---

## What is not added

- No separate audit or history table. The row's own fields — `AssignmentSource`, `AssignedBy`, `CreatedAt` — are the complete audit trail.
- No additional idempotency mechanism. A duplicate submission is rejected by the existing unique constraint.
- No new invocation edge. Creating a manual assignment is an assignment change like any other; 10.0 picks it up via its existing "after assignment changes" trigger.

**Source:** System Design Specification §17.1 (F1, G1, H1).

---

## Authorization

This process assumes the caller has already passed the applicable `PermissionTier` check. It does not itself define who is allowed to create a manual assignment.

This is identical to every configuration process's stated boundary — authorization is enforced upstream, consistently, everywhere in this specification.

**Source:** System Design Specification §17.1 (E1).

---

## Invariants

- Duty Rule's Role, Gender, Age Range, Tenure, Membership Stage, and Branch-Attendance Recency criteria do not gate manual assignment.
- Duty Rule's Eligibility Flag criterion does gate manual assignment, identically to how it gates automatic assignment.
- Slot capacity is not enforced.
- Per-occurrence availability is not enforced.
- (MemberID, DutyID, OccurrenceID) uniqueness is enforced, without exception.
- AssignmentStatusID is administrator-selected, not forced to NULL.
- 9.0 is invoked only when AssignmentStatusID is NULL at creation.
- Once in 7.0's lifecycle, a manually-created assignment is governed identically to an automatically-created one.
- AssignmentSource = Manual and AssignedBy are permanent provenance.
- 12.0 never modifies an existing row.
- 12.0 never writes to Service Occurrence.
- No new audit table is introduced.

**Source:** System Design Specification §17.5.

---

## Indexes

No new index is required. The uniqueness check is served by the existing `RosterAssignment (MemberID, DutyID, OccurrenceID)` unique constraint. The Eligibility lookup is served by the existing `Eligibility (MemberID, DutyID)` composite index.

**Source:** System Design Specification §17.6.

---

## Explicitly open implementation choices

- Whether the admin-facing interface warns when a selection would not satisfy Duty Rule's non-Eligibility criteria, versus allowing it silently. The contract permits the bypass either way.
- Whether a confirmation step exists between an admin's selection and the write (e.g., a review screen).
- Editing or removing an existing assignment — explicitly out of scope.

**Source:** System Design Specification §17.7.
