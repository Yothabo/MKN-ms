# 6.0 Record Attendance

*Records the raw fact of a member's presence at an occurrence. Derived from the System Design Specification §13. Where this document conflicts with the specification, the specification wins.*

---

## Responsibility

6.0 Record Attendance writes AttendanceRecord rows when a member's presence at an occurrence is registered. It is the narrowest process in the system — it reads two stores, writes one, and has no downstream consequences within the system's own logic.

Attendance is a raw fact. 6.0 does not interpret it, does not condition it on assignment, does not affect fill status, does not affect assignment status, and does not trigger any other process.

**Source:** System Design Specification §13.

---

## Trigger

Two triggers:

- **Manual register marking.** An administrator marks a member present at an occurrence, in the app or on the register table.
- **NFC tap.** A member taps a card or phone at the occurrence. The tap is ingested by the tap mechanism and produces an AttendanceRecord. The Tap path is defined in the vocabulary but is not produced by any implemented path in the current phase.

**Source:** System Design Specification §13.0, §13.1.1.

---

## The footprint

| Direction | Store |
| --- | --- |
| Reads | D4 (Member — to validate the member identity and to check attendance register eligibility), D3 (ServiceOccurrence — to identify which occurrence the record applies to; D3 also holds Branch.UsesAttendanceRegister for schedule-sourced occurrences), D9 (Event.UsesAttendanceRegister, for event-sourced occurrences), D11 (SystemSetting — `AttendanceRegisterEnabled`) |
| Writes | D8 (AttendanceRecord — one row per (MemberID, OccurrenceID) pair) |

**Never reads or writes:** D1, D2, D5, D6, D7, D9, D10, D12. Never modifies ServiceOccurrence in any field. Never writes FillStatusID. Never touches any assignment.

**Source:** System Design Specification §13.2, §9.6.

---

## The AttendanceRecord row

| Column | Value |
| --- | --- |
| RecordID | System-generated |
| MemberID | The member whose presence is recorded |
| OccurrenceID | The occurrence at which presence is recorded |
| Timestamp | The moment the record is written |
| Source | Manual or Tap. Manual is produced by the manual register marking path. Tap is defined but not produced by any implemented path. |

The row is the raw fact.

**Source:** System Design Specification §13.1.1, §13.1.4.

---

## Attendance register scope

The attendance register's on/off state is configured at three scopes. The most specific scope in effect wins.

- **Global.** A System Setting names the default state.
- **Per-event.** `Event.UsesAttendanceRegister`. Null means no override.
- **Per-branch.** `Branch.UsesAttendanceRegister`. Null means no override.

The resolution order depends on the occurrence's source:

- Schedule-sourced occurrence: branch override of the branch in the occurrence's time slot, then the global `AttendanceRegisterEnabled`.
- Event-sourced occurrence: event override, then the global `AttendanceRegisterEnabled`.

When the register is off at the effective scope:

- 6.0 does not write AttendanceRecord rows for occurrences at that scope. Manual marking is disabled. The tap path is disabled.
- The `Branch-Attendance Recency` Duty Rule criterion is skipped for those occurrences, as stated in the 5.0 document.
- The Attendance Rule engine does not apply absence-based rules to members whose effective scope is off.

When the register is on at the effective scope, 6.0 records normally.

The register may also be used for counting attendance at events, and for youth fundraising taps. These uses are records, not rostering signals, and they operate independently of the criterion-skip behaviour.

**Source:** System Design Specification §9.6, §10.1.5.

---

## Attendance register eligibility

A member is eligible for the attendance register only if they hold a ReceiptNumber or a CardNumber. Both are issued from the configured minimum age upward. Below that age, no identifier is issued, and the member is not eligible for attendance tracking.

The configured minimum age is a System Setting, corresponding to the same threshold that governs identifier issuance.

**Source:** System Design Specification §4 (Member), §9.1.7.

---

## Uniqueness

`AttendanceRecord` permits at most one recorded attendance fact for a given (MemberID, OccurrenceID) pair. The uniqueness constraint is the integrity guard.

A subsequent tap or manual mark for an existing pair is a no-op. It does not create a second row, and the application-level check treats it as a no-op rather than an error.

This makes 6.0 idempotent per (MemberID, OccurrenceID). Re-running the same tap produces no new row.

**Source:** System Design Specification §13.1.2.

---

## Independence from assignment

6.0 does not check whether the member is assigned to the occurrence. A member may be:

- Rostered and attend.
- Rostered and not attend.
- Not rostered and attend.
- Not rostered and not attend.

All four are valid states. Attendance is a fact; assignment is a plan. The system does not conflate them.

**Source:** System Design Specification §13.1.3.

---

## Branch-agnostic attendance

Attendance is recorded against the occurrence, not the member's home branch. A member attending at a branch other than their home branch produces an attendance record against that occurrence, with no reference to Member.BranchID.

This is consistent with the MKN Configuration Reference's branch-agnostic attendance default.

**Source:** System Design Specification §13.1.3.

---

## No attendance-window enforcement

No attendance-window enforcement is performed by 6.0 or the schema. The system does not prevent attendance before, during, or after the occurrence's scheduled window. Any such enforcement, if introduced, is outside the current contract.

**Source:** System Design Specification §13.3.

---

## Manual administrator entry

An administrator may add an attendance record directly — for a member whose tap failed, for a retrospective correction, or for another operational reason. The row is identical to a tap-initiated one except for the Source value, which is Manual.

**Source:** System Design Specification §13.1.4.

---

## No interpretation layer

6.0 does not compute attendance recency, does not update any cache or derived field, and does not apply any status change. The `Branch-Attendance Recency` criterion reads AttendanceRecord at evaluation time. The Attendance Rule engine — process 13.0 — is the process that reads attendance over time and applies status changes. 6.0 and 13.0 are separate: 6.0 writes the fact; 13.0 evaluates the fact.

**Source:** System Design Specification §13.1.5, §13.6.

---

## Invariants

- Raw fact. Attendance is a fact of presence, not an interpretation. 6.0 writes it and stops.
- Uniqueness. AttendanceRecord permits at most one recorded attendance fact for a given (MemberID, OccurrenceID) pair.
- Idempotent per member per occurrence. Re-running the same tap produces no new row.
- Independence from assignment. Attendance is not conditioned on RosterAssignment.
- Branch-agnostic. Attendance is recorded against the occurrence, not the member's home branch.
- Scope-aware. When the register is off at the effective scope, no row is written.
- Eligibility-aware. Only members with a ReceiptNumber or CardNumber are tracked.
- No attendance-window enforcement.
- No interpretation. 6.0 does not compute recency, streaks, or any derived value.
- No downstream trigger beyond the fact that the Attendance Rule engine reads what 6.0 writes.
- No notification.
- No assignment or fill-status side effect.

**Source:** System Design Specification §13.3.

---

## Candidate access patterns

- **`AttendanceRecord (MemberID, OccurrenceID)` — UNIQUE.** The integrity guard. Also serves the existence check.
- **`AttendanceRecord (OccurrenceID)`.** Natural access pattern for "who attended this occurrence" queries.
- **`AttendanceRecord (MemberID, Timestamp)`.** Natural access pattern for Branch-Attendance Recency evaluation by 5.0, for the Attendance Rule engine's absence check, and for member-facing attendance history.

Physical forms are implementation-dependent.

**Source:** System Design Specification §13.4.
