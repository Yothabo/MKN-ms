# 5.0 Generate Assignment

*Fills the required duty slots of a Service Occurrence by creating Roster Assignment records. Derived from the System Design Specification §10. Where this document conflicts with the specification, the specification wins.*

---

## Responsibility

5.0 Generate Assignment fills the required duty slots on a Service Occurrence by producing Roster Assignment rows. It reads Eligibility to determine candidacy, reads Duty Rule to rank candidates, and writes assignments.

It is the process where the configuration language actually does something. Every Duty Rule, Eligibility grant, and Service Definition Duty is executed here.

**Source:** System Design Specification §10.

---

## Trigger

Two triggers, sharing identical logic:

- **Scheduled run.** A recurring run that picks up any occurrence not yet filled, or any occurrence whose assignments have become incomplete.
- **Manual administrator action.** An administrator can invoke the process for a specific occurrence or date range.

5.0 is never invoked by 11.0. The two processes are independent; scheduling may run them close together so newly materialized occurrences are filled promptly, but neither calls the other.

**Source:** System Design Specification §10.0, §10.5.

## The footprint

| Direction | Store |
| --- | --- |
| Reads | D2 (DutyRule), D3 (ServiceOccurrence, ServiceDefinitionDuty, ServiceOccurrenceDuty, BranchTimeSlot), D4 (Member), D6 (Eligibility), D7 (RosterAssignment — capacity count and availability check), D8 (AttendanceRecord — only when a Branch-Attendance Recency criterion is present) |
| Writes | D7 (RosterAssignment inserts only) |
| Invokes | 9.0 Dispatch Notification, on each new automatic assignment |

**Never reads or writes:** D1, D5, D9, D10, D11, D12. Never modifies ServiceOccurrence. Never modifies existing RosterAssignment rows.

**Source:** System Design Specification §10.2.

---

## The two-mechanism model

5.0 applies two distinct mechanisms, and they are never allowed to collapse into each other:

**Eligibility gates candidacy.** A member is a candidate for a duty if and only if they are eligible for that duty. Eligibility is a binary, administrator-granted permission record.

**Duty Rule ranks candidates.** Duty Rule orders eligible candidates by tier. It does not determine who is a candidate; it determines the order of preference among those who already are.

The two are independent. A member can be eligible and fail every Duty Rule, or ineligible and match every Duty Rule — in which case they never become a candidate at all.

**Source:** System Design Specification §10.1.4, §10.1.5.

---

## Eligibility resolution

For each (Member, Duty) pair, 5.0 determines eligibility by resolving the applicable Eligibility row:

1. The row whose GrantedDate is in the past.
2. Whose RevokedDate is either null or in the future.
3. If multiple such rows exist, the one with the greatest EligibilityID is used as the deterministic tiebreaker.

If the resolved row has a RevokedDate in the past, the member is not eligible. If no row exists at all, the member is not eligible. Eligibility is opt-in.

**Source:** System Design Specification §10.1.4.

---

## Duty Rule evaluation

Tiers are evaluated in ascending TierOrder. For each tier:

1. All rules sharing that TierOrder are combined with AND.
2. A member matches the tier if every rule at that tier evaluates true for them.
3. The first tier producing at least one eligible, available candidate supplies the candidate set.

If no Duty Rules exist for a duty, every eligible member enters as an equal candidate.

If a tier consists entirely of rules whose criteria types are reserved (Acceptance Rate, Duties Carried, Days Since Last Assignment), the tier is treated as producing no candidates.

**Source:** System Design Specification §10.1.5, §5.

---

## Criteria evaluation

| CriteriaType | Evaluation |
| --- | --- |
| Role | Member's RoleID matches the rule's CriteriaValue (resolved by name) |
| Gender | Member's Gender matches |
| Age Range | Computed from DateOfBirth and today's date, within the range |
| Tenure | Computed from JoinDate and today's date, meets the threshold |
| Membership Stage | Member's MembershipStage matches |
| Branch-Attendance Recency | Member has an AttendanceRecord at the specified branch within the configured window |
| Eligibility Flag | Member has a current Eligibility grant for the referenced duty |

Each criterion is a mechanical evaluation against the member's stored data. The system does not interpret the criterion beyond what its type defines.

**Source:** System Design Specification §10.1.5.

## Availability

A member is available for a duty on an occurrence if and only if they do not have a **non-terminal** Roster Assignment on that OccurrenceID.

Terminal assignments — those whose AssignmentStatusID references a status with `IsTerminal = true` — do not block availability. They represent slots the member no longer occupies.

The availability rule uses `AssignmentStatus.IsTerminal`, the same boolean used by 7.0's re-resolution logic and 10.0's capacity calculation.

**Source of the rule.** The occurrence-level exclusion is a fixed default the system applies. It is not a configurable rule in the current specification, and it is not a rule the assignment process is free to alter. The process applies it because the specification states it as the mechanical default.

**Specification gap.** A future revision may define a configurable override that permits a member to hold more than one duty on the same occurrence when the administrator configures it — for example, where two duties are carried by the same role and only one such member is available. That override would be expressed through the Duty Rule criteria vocabulary. **The current criteria vocabulary (see Specification §5) does not include a criterion that evaluates a member's existing assignments on the same occurrence, and therefore cannot currently express this exception.** No such criterion is introduced by this specification. The absence is recorded here so that any future addition is a deliberate specification change, not a silent invention.

**Source:** System Design Specification §10.1.2.

---

## Capacity — the slot-count rule

For each (OccurrenceID, DutyID) pair, the effective slot count is determined by:

1. The RequiredSlotCount from ServiceDefinitionDuty for the duty.
2. Overridden by ServiceOccurrenceDuty.RequiredSlotCount if an override row exists with Action = Added.
3. If a ServiceOccurrenceDuty row exists with Action = Removed, the duty is not required for that occurrence, and no slots are filled.

5.0 counts existing non-terminal assignments for the pair and fills up to the remaining count. Terminal assignments do not count toward the total.

**Source:** System Design Specification §10.1.3.

---

## Selection within a tier

When a tier produces more candidates than slots, 5.0 fills from the candidate set in a deterministic order. The order is defined by 5.0 (candidate ordering by ascending MemberID is a defensible concrete choice).

No fairness guarantee is made. No rotation, load-balancing, or recency-based ordering is applied. Reserved fairness criteria may activate later, at which point a tier using them produces a meaningfully ordered candidate set.

**Source:** System Design Specification §10.1.6.

---

## One member, one occurrence

5.0 does not assign a member to more than one duty on the same occurrence. If a member is already assigned to any duty on an occurrence (with a non-terminal status), they are excluded from candidacy for any further duty on that occurrence.

This is the availability rule from B7. The distinction is worth preserving: it is not "one member, one duty" in the abstract — it is "one member, one assignment on this occurrence."

**Source:** System Design Specification §10.1.2.

---

## No fallback

If no tier produces a candidate, the duty's slots remain unfilled. No fallback to lower tiers. No notification of non-assignment.

If fewer candidates exist than slots, the remaining slots remain unfilled. No top-up from lower tiers.

**Source:** System Design Specification §10.1.5.

---

## Additivity

5.0 never removes or modifies an existing Roster Assignment. It is additive. If a duty already has some assignments, 5.0 fills only the remaining slots.

Removal or replacement is a 7.0 concern (on decline or timeout) or an explicit administrator action.

**Source:** System Design Specification §10.1.7.

---

## Initial status

5.0 writes assignments with `AssignmentStatusID = NULL`. The assignment lifecycle begins with 7.0; 5.0 does not claim a lifecycle state.

It also writes:

- `AssignmentSource = Automatic`
- `AssignedBy = NULL`
- `ApprovedBy = NULL`
- `CreatedAt` = the moment of insertion

**Source:** System Design Specification §10.1.1.

---

## Uniqueness

Roster Assignment is unique on (MemberID, DutyID, OccurrenceID). This is the database-level guard against duplicate records, regardless of source.

The capacity rule (counting assignments per (OccurrenceID, DutyID) up to RequiredSlotCount) governs how many slots are filled. The uniqueness rule governs what combinations may coexist. Both are required.

**Source:** System Design Specification §10.1.7.

---

## Re-entry

5.0 is fully re-entrant. An interrupted run resumes on the next run; existing assignments are counted, remaining slots are filled. No checkpoint state.

**Source:** System Design Specification §10.1.7.

---

## Interaction with 9.0

When 5.0 creates a new automatic assignment, it invokes 9.0 Dispatch Notification with that assignment as input. 9.0 sends an assignment notice to the member.

The invocation is fire-and-forget. 5.0 does not wait for the notification result; 9.0's failure does not roll back the assignment.

No other process is invoked by 5.0.

**Source:** System Design Specification §10.1.8.

---

## Manual assignments

An administrator can create a Roster Assignment manually, bypassing 5.0's candidate selection. The row carries `AssignmentSource = Manual` and `AssignedBy = <AdminID>`.

A manual assignment can violate Eligibility — the administrator is assumed authorized to override. The (MemberID, DutyID, OccurrenceID) uniqueness constraint applies regardless of source.

The MKN Configuration Reference sets a default that manual assignments are excluded from future fairness signals. This is a policy, not a system rule.

**Source:** System Design Specification §10.1, MKN Configuration Reference.

---

## Invariants

- Eligibility gates candidacy; Duty Rule only ranks.
- Tiers are evaluated in ascending TierOrder.
- Same-tier rules are ANDed.
- No tier → every eligible member is an equal candidate.
- No candidate in any tier → slot remains unfilled, no fallback.
- Fewer candidates than slots → remaining slots unfilled, no top-up.
- 5.0 never removes or modifies an existing assignment.
- 5.0 does not assign a member to more than one duty on the same occurrence.
- (MemberID, DutyID, OccurrenceID) is unique in RosterAssignment.
- 5.0 is fully re-entrant.
- AssignmentStatusID is null at creation.
- AssignmentSource = Automatic, AssignedBy = null for automatic assignments.
- 5.0 never writes FillStatusID.
- 5.0 never modifies ServiceOccurrence.
- 5.0 invokes only 9.0.
- 5.0 is independent of 11.0.

**Source:** System Design Specification §10.3.

## Candidate access patterns

- **`RosterAssignment (MemberID, DutyID, OccurrenceID)` — UNIQUE.** The integrity guard.
- **`RosterAssignment (OccurrenceID, DutyID)`.** Serves the capacity count and availability check. Hot path for filling slots.
- **`Eligibility (MemberID, DutyID)`.** Serves eligibility resolution.
- **`DutyRule (DutyID, TierOrder)`.** Serves tier evaluation.

Physical forms are implementation-dependent.

**Source:** System Design Specification §10.4.
