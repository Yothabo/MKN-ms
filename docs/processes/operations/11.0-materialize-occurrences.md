
# 11.0 Materialize Occurrences

*Generates Service Occurrence records from active Service Schedules on a rolling time horizon. Additive and idempotent. Derived from the System Design Specification §7 and §8. Where this document conflicts with the specification, the specification wins.*

---

## Responsibility

11.0 Materialize Occurrences is a system-internal, time-triggered process that ensures Service Occurrence rows exist for every active Service Schedule up to a configured horizon, expressed in days.

It is the process that produces the *what* of the roster — the occurrence exists. Filling it with members is 5.0's responsibility.

**Source:** System Design Specification §7.

---

## Trigger

Two triggers, sharing identical logic:

- **Scheduled run.** Daily, using the application's existing scheduled-job mechanism. The frequency is fixed, not administrator-configurable.
- **Manual run.** An administrator can invoke the process with an explicit horizon in days. A smaller manual horizon is a safe no-op for dates already covered.

Neither trigger invokes the process indirectly. 11.0 is not invoked by any other process.

**Source:** System Design Specification §7 (Trigger and scheduling).

---

## The central invariant

**The Occurrence Materializer is additive and idempotent. It creates missing schedule-sourced occurrences within the configured horizon and never modifies or deletes an occurrence that already exists.**

This is the load-bearing rule of the entire process. Every other property derives from it.

**Source:** System Design Specification §7 (The resulting invariant).

## The lifecycle

```

Active ServiceSchedule
│
▼
Within [today, today + N]
│
▼
Occurrence already exists?
├── YES → do nothing
└── NO  → INSERT

```

Where N is `OccurrenceHorizonDays` from D11.

**Source:** System Design Specification §7 (Occurrence creation contract).

---

## Horizon configuration

`OccurrenceHorizonDays` is a required System Setting:

- Type: integer, unit days
- Minimum: 0 (0 means materialize today only)
- Global, not per-branch or per-schedule
- No system-assumed default

If unconfigured, the Materializer refuses to run and surfaces a configuration error. It does not idle silently. A change to the horizon takes effect on the next run; changing the setting is not itself a trigger.

**Source:** System Design Specification §7 (Horizon configuration).

---

## Schedule eligibility

A schedule is eligible for materialization when the schedule itself is active, its Service Definition is active, and its Branch Time Slot is active. All three must be active for the schedule to produce occurrences.

**Source:** System Design Specification §7 (Schedule lifecycle interaction).

---

## Occurrence creation contract

For each active schedule:

1. Generate candidate dates from today through today + horizon, inclusive, using the configured system/application timezone.
2. For each date, check whether a Service Occurrence already exists for that (ScheduleID, Date) pair.
3. If one exists, do nothing.
4. If not, insert one with:
   - `ScheduleID` = the schedule's ID
   - `Date` = the missing date
   - `ServiceTypeID` = inherited from the schedule's Service Definition
   - `StartTime` = inherited from the schedule
   - `FillStatusID` = null
   - `GeneratedBy` = System
   - `CreatedBy` = null
   - `ChangedBy` = null

Each occurrence commits in its own transaction. The process is fully re-entrant — an interrupted run simply leaves remaining dates for the next run to fill.

**Source:** System Design Specification §7 (Occurrence creation contract).

---

## Idempotency

The process is idempotent because of one rule: a date that already has a ServiceOccurrence row — system-generated or carrying an administrator override — is never touched again on a later run.

This is what guarantees that an override made today for a service three weeks out can never be silently overwritten by a subsequent run. The override survives.

The uniqueness constraint on (ScheduleID, Date) for schedule-sourced rows is the correctness guard at the database level. The application-level existence check is a pre-write optimization.

**Source:** System Design Specification §7 (Immutability), §8.1.3.

---

## Immutability

An existing occurrence is never updated or deleted by 11.0. No exception. Cancellation is represented through the Outcome State, not row deletion. No tombstone mechanism exists.

`GeneratedBy` is permanent provenance, set once at creation and never altered. `ChangedBy` separately records any later human modification.

**Source:** System Design Specification §7 (Immutability).

---

## Time handling

- `Date` is date-only. Start time is represented separately on the occurrence and is unaffected by this process.
- The process uses the configured system/application timezone. Not a per-branch timezone; "today" must have one deterministic calendar meaning.
- No daylight-saving-specific logic exists in this process. The existing schedule start time is treated as a plain wall-clock value.
- No holiday or blackout exclusions are built in.

**Source:** System Design Specification §7 (Time handling).

---

## Schedule lifecycle interaction

- **Newly created schedule:** picked up automatically on the next run.
- **Schedule change:** occurrences already materialized from it are never rewritten.
- **Schedule deactivation:** existing occurrences remain; the schedule stops being eligible for future generation. Deactivation, not deletion, is the mechanism for stopping generation.
- **Service Definition duty composition change:** never propagated backward into already-materialized occurrences.

**Source:** System Design Specification §7 (Schedule lifecycle interaction).

---

## Zero-duty occurrences

An occurrence is created even if its Service Definition currently has zero configured duties. The existence of a scheduled service is independent of whether duties have been configured for it.

**Source:** System Design Specification §7 (Occurrence creation contract).

---

## Service Occurrence Duty

11.0 does not create Service Occurrence Duty rows. Those represent per-occurrence overrides created by an administrator. An occurrence with no override simply inherits its Service Definition's duty list.

**Source:** System Design Specification §7 (Occurrence creation contract).

---

## Operational visibility

Each run produces one Materializer Run record in D12:

- TriggerType (Scheduled or Manual)
- TriggeredBy (Admin, populated only when Manual)
- StartedAt, CompletedAt
- SchedulesEvaluated, OccurrencesCreated
- Status (Success or Failure)
- ErrorDetail (populated on failure)

A failed run is recoverable simply by running again. No separate retry or incident subsystem exists. No dry-run mode and no un-materialize operation exist.

**Source:** System Design Specification §7 (Operational visibility), §8.1.5.

---

## Event-sourced occurrences

Occurrences created when an administrator links a Program Item to a Service Definition are entirely outside this process. They carry `GeneratedBy = Administrator` and `CreatedBy` = the admin who created them. Their uniqueness is governed by the Event/Program process, not by the (ScheduleID, Date) rule.

**Source:** System Design Specification §7 (Event-sourced occurrences).

---

## Explicit non-relationships

- Independent of Assignment generation. Never invokes 5.0.
- Never sends a notification. Never invokes 9.0.
- Never touches 10.0, 6.0, or 7.0.
- No readiness flag is produced; 5.0 queries occurrences directly.
- OwningBranch enforcement is not this process's concern. It consumes already-valid schedules.

**Source:** System Design Specification §7 (Explicit non-relationships).

---

## Invariants

- **Additive.** No UPDATE or DELETE against ServiceOccurrence.
- **Idempotent.** Repeated runs produce no new rows once coverage is complete.
- **Horizon boundedness.** No row created with Date outside [today, today + N].
- **Schedule-source attribution.** Every created row has a non-null ScheduleID, GeneratedBy = System, CreatedBy = null, ChangedBy = null, FillStatusID = null.
- **Provenance immutability.** GeneratedBy never changes.
- **Schedule deactivation preserves existing rows.** No cascade.
- **Schedule change does not rewrite existing occurrences.**
- **Service Definition change does not propagate backward.**
- **Full re-entrancy.** No checkpoint state.
- **Manual and scheduled runs produce identical results** for the same horizon and time.
- **Required-setting failure.** Missing OccurrenceHorizonDays → zero rows written, one Materializer Run with Status = Failure.
- **Uniqueness.** No two schedule-sourced rows share (ScheduleID, Date).
- **Event-sourced exclusion.** Never creates, modifies, or deletes a row with a non-null EventID.
- **Zero-duty occurrence creation.** Even with no duties, the occurrence exists.
- **Timezone determinism.** "Today" resolves to a single calendar date.
- **No outbound flow.** No notification, no assignment generation, no writes outside D3 and D12.

**Source:** System Design Specification §8.3.

---

## Candidate access patterns

- **`ServiceOccurrence (ScheduleID, Date)` — UNIQUE, restricted to schedule-sourced rows.** The correctness guard and the backing index for the existence check.
- **`ServiceSchedule (IsActive) where IsActive = true`.** Serves the query for active schedules.

Both are candidate indexes; the physical form is implementation-dependent.

**Source:** System Design Specification §8.4.
