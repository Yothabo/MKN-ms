# 9.0 Dispatch Notification

*Sends assignment notices to members through the configured channel. Fire-and-forget. Derived from the System Design Specification §14. Where this document conflicts with the specification, the specification wins.*

---

## Responsibility

9.0 Dispatch Notification is the outbound process that sends assignment notices to members. It is invoked by 5.0, 7.0, and 12.0 when they create assignments that require a response — meaning an assignment created with no status. It is the only process in the system whose primary effect is an external side effect rather than a write to an internal data store.

It reads the assignment, the member, the occurrence, and the configured channel, composes a message, sends it, and stops. It does not write to any store, does not track delivery, does not retry, and does not invoke any other process.

**Source:** System Design Specification §14.

---

## Trigger

9.0 has two triggers, on two distinct paths.

**Path 1 — member-facing, invoked.** Invoked by three processes, under the conditions below:

| Invoked by | When |
| --- | --- |
| 5.0 Generate Assignment | On each new automatic assignment created |
| 7.0 Manage Confirmation | On each replacement assignment created after decline or timeout |
| 12.0 Create Manual Assignment | Only when the created manual assignment has AssignmentStatusID = NULL at creation |

**Path 2 — authority-facing, scheduled.** A scheduled authority-notification sweep runs 9.0 on a cadence. On each run, 9.0 reads new ConfigurationAuditLog entries and dispatches notifications for them. See the Authority Notifications section below.

9.0 is not invoked on:

- Status changes to an existing assignment (confirm, decline, timeout).
- Fill status changes by 10.0.
- Attendance records by 6.0.
- Any occurrence materialization.

**Invocation versus triggering.** The three rows in Path 1 are invocations: 5.0, 7.0, and 12.0 call 9.0 directly. Path 2 is a trigger, not an invocation. No process calls 9.0 for the authority-notification sweep; the scheduler starts 9.0 directly. The durable invariant — that 9.0 is the sole process any other process is permitted to invoke — concerns invocation, not triggering, and is unaffected by Path 2.

**Source:** System Design Specification §14.1.3, §16.0, §16.4, §16.6.

## Authority Notifications

The authority-notification path informs admins of configuration events — deactivations and soft deletes — recorded in the ConfigurationAuditLog. It is the second trigger path for 9.0.

### Signal store

ConfigurationAuditLog is the signal store. Every configuration deactivation and every configuration soft delete writes a row. The row carries the entity type, entity ID, entity name, action, reason, who initiated, who approved, timestamps, and the consequences previewed and occurred. It also carries `NotifiedAt`, which is null until the notification sweep has processed it.

### The sweep

9.0 runs a scheduled authority-notification sweep. On each run, it reads every ConfigurationAuditLog row where `NotifiedAt IS NULL`. For each, it matches NotificationSubscription rows by `EventType`. For each matching subscription, it resolves the recipient or recipients — by permission tier, or by specific admin. It composes a message from the audit entry. It sends the message through the configured channel. It sets `NotifiedAt` on the audit row.

### Recipients

Recipients are configured in NotificationSubscription. A subscription row names either a permission tier or a specific admin, never both. When the tier is named, every admin of that tier receives the notification. When a specific admin is named, only that admin receives it. Multiple subscriptions may match a single audit entry, in which case multiple notifications are sent — one per recipient or per resolved recipient set.

### What is and is not recorded

The audit row records that a notification was dispatched, by setting `NotifiedAt`. Delivery itself is not tracked. There is no delivery log, no retry, no receipt confirmation. This is consistent with the member-facing path.

### Fire-and-forget

The sweep does not wait for a delivery result. If the underlying channel fails, the notification is lost from the system's perspective, and the audit row is still marked as notified. This is the same behaviour the member-facing path has always had.

### The channel

The channel is the same for both paths. The `NotificationChannel` setting names the transport. The message content is composed differently — a member notice requests a response, an authority notice states what happened.

**Source:** System Design Specification §14.1.3, §16.0, §16.4, §16.6.

## The trigger boundary

9.0's trigger is bounded to exactly one condition: a new RosterAssignment row has been created that requires a response. It is invoked by the three processes that create such assignments (5.0 for automatic, 7.0 for replacements, 12.0 for manual assignments created with no status).

Status changes on an existing assignment do not trigger 9.0. Fill status changes do not trigger 9.0. Attendance records do not trigger 9.0.

**Source:** System Design Specification §14.1.3.

---

## Channel selection

9.0 reads `SystemSetting.NotificationChannel`. If the setting is absent or otherwise invalid, 9.0 follows the system setting's configured validity behavior; no channel-specific fallback is defined by this contract.

The setting names the channel — SMS, email, push, or another mechanism — and the actual credentials and transport live outside the schema.

Whether `NotificationChannel.Required` is true or false is a configuration choice, not fixed by the 9.0 contract. If it is configured as required and absent, 9.0 refuses to send and the system surfaces a configuration error, consistent with the required-setting pattern used elsewhere. If it is configured as optional and absent, no notification is sent.

The current scope assumes a single global channel. Per-member channel preferences are not modeled.

**Source:** System Design Specification §14.1.2.

---

## No writes

9.0 does not write to any store. It has no persistence side effect. The notification is composed, sent, and forgotten — from the system's perspective.

This is a deliberate design choice: introducing a notification log, retry table, or delivery-status field would be new infrastructure. No delivery outcome is observable by the system. If a member does not respond to an assignment, 7.0 may eventually time it out according to its normal timeout rules, regardless of whether the absence of response resulted from notification failure.

**Source:** System Design Specification §14.1.1.

---

## No delivery tracking

The system does not record that a notification was sent, when, through which channel, or whether it was delivered. There is no NotificationLog.

If audit or delivery tracking becomes a requirement, it is an additive structure — not part of the current contract.

**Source:** System Design Specification §14.1.4.

---

## No retry

If the underlying channel fails, the notification is lost from the system's perspective. 9.0 does not retry.

**Source:** System Design Specification §14.1.5.

---

## Message content

The notification carries enough information for the member to understand what they are being asked to respond to: the occurrence date and time, the duty, and (implicitly) the expectation of a response. The exact format is channel-dependent and outside the schema.

The notification does not contain a confirmation token or other schema-defined response identifier. Assignment-response correlation is handled by the 7.0 response mechanism and is outside 9.0's schema contract.

**Source:** System Design Specification §14.1.6.

---

## Fire-and-forget

9.0's invocation is fire-and-forget. Its success or failure does not affect the invoking process's state. The invoking process does not wait for the notification result.

Whether the invocation is synchronous or asynchronous from the invoking process's perspective is an implementation choice. It does not create a semantic dependency.

**Source:** System Design Specification §14.3.

---

## Invariants

- Outbound only. 9.0's only product is a message sent to a member.
- Read-only on all stores. 9.0 reads what it needs; it writes nothing.
- Trigger is bounded. Invoked only by 5.0, 7.0, and 12.0, only on new assignment creation that requires a response.
- No invocation on status change.
- No invocation on any other event.
- Channel selected by setting. Follows the setting's configured validity behavior; no channel-specific fallback.
- Fire-and-forget.
- No retry.
- No delivery log.
- No token. The notification does not contain a confirmation token or other schema-defined response identifier.
- Channel-agnostic contract. SMS, email, push, and others are acceptable implementations behind the same contract.

**Source:** System Design Specification §14.3.

---

## Indexes

9.0 does not require any indexes. It reads by primary key from RosterAssignment, Member, and ServiceOccurrence, and by key from SystemSetting. All are served by existing primary-key or foreign-key indexes.

No index is prescribed at specification level for 9.0.

**Source:** System Design Specification §14.4.
