# 7.0 Manage Confirmation

*Tracks each Roster Assignment's response lifecycle. Re-resolves only the affected slot on a decline or timeout. Derived from the System Design Specification §11. Where this document conflicts with the specification, the specification wins.*

---

## Responsibility

7.0 Manage Confirmation tracks the response lifecycle of each Roster Assignment. It transitions the assignment's AssignmentStatusID from NULL (as written by 5.0) through the administrator-defined statuses, and on decline or timeout it re-resolves only the affected slot.

7.0 owns the assignment status lifecycle. 5.0 creates the assignment; 7.0 moves it through its lifecycle.

**Source:** System Design Specification §11.

---

## Trigger

Two triggers, within the same process:

- **Member response.** A confirm or decline signal arrives from a member.
- **Scheduled check.** Runs periodically to detect timed-out assignments.

**Source:** System Design Specification §11.0.

## Status lifecycle ownership

5.0 creates automatic assignments with `AssignmentStatusID = NULL`. 7.0 owns the status transitions for assignments after creation.

Other processes — for example, a manual assignment operation — may also create assignments with `AssignmentStatusID = NULL`. Once an assignment exists, 7.0 is the process that moves it through its lifecycle.

**Source:** System Design Specification §11.1.4.

---

## Initial status

7.0 transitions an assignment from NULL to the administrator-designated initial status. This status is identified via `SystemSetting.InitialAssignmentStatusID`, a required setting.

If the setting is unset or invalid, 7.0 refuses to run and surfaces a configuration error.

**Source:** System Design Specification §11.1.5.

---

## Status transitions

The system does not enforce a state machine. Any transition between statuses is permitted at the schema level. The lifecycle semantics — which transitions are meaningful — are the administrator's concern. The system records the current AssignmentStatusID and nothing else.

**Source:** System Design Specification §11.1.3.

---

## Timeout

An assignment becomes eligible for timeout when its elapsed age reaches the configured ConfirmationTimeoutHours:
now - CreatedAt >= ConfirmationTimeoutHours

The timeout check runs as a scheduled part of 7.0.

If ConfirmationTimeoutHours is unset and Required = false, no timeout occurs. If Required = true and the setting is unset, 7.0 refuses to run and surfaces a configuration error.

**Source:** System Design Specification §11.1.6.

---

## Terminal statuses

`AssignmentStatus.IsTerminal` distinguishes statuses that occupy a required slot from statuses that leave the slot vacant. A status marked `IsTerminal = true` does not count toward the effective required slot count.

`IsTerminal` is a capacity concept, not a lifecycle-impermanence concept. A terminal assignment's row remains, and the member may rejoin a slot through a new assignment.

For re-resolution to occur on a decline or timeout, the decline and timeout statuses must be marked terminal. This is a configuration concern — the administrator is responsible for setting IsTerminal correctly.

**Source:** System Design Specification §11.1.2.

---

## Re-resolution on decline or timeout

When a member declines or an assignment times out:

1. The assignment's AssignmentStatusID transitions to the administrator-designated declined or timed-out status.
2. If the status is not marked terminal, the slot remains occupied and no re-resolution occurs.
3. 7.0 runs the same candidate selection logic 5.0 uses, scoped to the affected (OccurrenceID, DutyID) slot only.
4. **The declining or timed-out member is explicitly excluded from the replacement candidate set for the affected slot.** Their terminal assignment does not exclude them under the general availability rule — terminal assignments do not block availability. This exclusion is an additional 7.0 rule specific to re-resolution.
5. If a candidate is found, a replacement RosterAssignment row is inserted with AssignmentStatusID = NULL, AssignmentSource = Automatic, AssignedBy = NULL, and 7.0 invokes 9.0 for the notification.
6. If no candidate is found, the slot remains vacant. No fallback. No escalation from 7.0.

The declining or timed-out row is never modified beyond the status transition. Its history is preserved.

**Source:** System Design Specification §11.1.7.

---

## The availability/exclusion distinction

Two different rules apply to the declining or timed-out member:

**General availability (5.0):** a member with a non-terminal assignment on the occurrence is unavailable. Once the declined assignment becomes terminal, that assignment no longer blocks availability.

**7.0 re-resolution exclusion:** the member whose assignment just became terminal is explicitly excluded from the replacement candidate set for that slot in that cycle.

These are distinct. The first is a data condition; the second is a rule 7.0 applies.

**Source:** System Design Specification §11.1.7.

## Replacement fields

A replacement assignment produced by 7.0's re-resolution carries:

| Column | Value |
| --- | --- |
| AssignmentSource | Automatic |
| AssignedBy | NULL |
| ApprovedBy | NULL |
| AssignmentStatusID | NULL |
| CreatedAt | The moment of insertion |

7.0 does not produce manual assignments.

**Source:** System Design Specification §11.1.1, §11.1.7.

---

## Interaction with 9.0

7.0 invokes 9.0 only when it creates a replacement assignment. It does not invoke 9.0 on status changes of existing assignments — a status change is the member's own action being recorded, and notifying them of their own action would be redundant.

The invocation is fire-and-forget. 9.0's failure does not roll back the replacement assignment.

**Source:** System Design Specification §11.1.8.

---

## Invariants

- 5.0 creates automatic assignments with AssignmentStatusID = NULL; 7.0 owns status transitions after creation.
- Status transitions are unrestricted at the schema level.
- Timeout rule: `now - CreatedAt >= ConfirmationTimeoutHours`.
- Required-setting failure: missing InitialAssignmentStatusID or required ConfirmationTimeoutHours → 7.0 refuses to run.
- Terminal statuses leave slots vacant.
- Replacement is additive; the declined/timed-out row is not modified beyond the status transition.
- History preserved; terminal rows are never deleted.
- Re-resolution scoped to the affected slot only.
- Declining member explicitly excluded from the replacement candidate set.
- No automatic re-resolution when no candidate is found.
- 9.0 invoked only on replacement creation.
- Fire-and-forget notification.
- No downstream trigger besides 9.0.
- No fill-status evaluation.
- No occurrence modification.
- No attendance record.
- Slot capacity preserved under concurrency (transactional control required).

**Source:** System Design Specification §11.3, §11.5.

## Candidate access patterns

- **`RosterAssignment (CreatedAt)`.** Serves the scheduled timeout check.
- **`RosterAssignment (OccurrenceID, DutyID, AssignmentStatusID)`.** Serves affected-slot resolution during re-resolution.

Physical forms are implementation-dependent.

**Source:** System Design Specification §11.4.
