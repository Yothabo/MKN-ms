# 1.0 Configure Vocabulary

*Creates and maintains the administrator-defined vocabulary the rest of the configuration layer consumes. Derived from the System Design Specification §9. Where this document conflicts with the specification, the specification wins.*

---

## Responsibility

1.0 Configure Vocabulary establishes the system's base vocabulary. It creates and maintains Roles, Duties, Branches, Branch Time Slots, Service Definitions, Service Definition Duties, Service Schedules, and the D10 lookup values (Outcome State, Assignment Status, Permission Tier, TimeOfDay, ServiceType).

Its output is inert configuration data. It does not evaluate, does not link, and does not interpret. A Duty created by 1.0 with no Duty Rule and no Service Definition Duty reference is valid but operationally unused.

**Source:** System Design Specification §9.1.2 – §9.1.6, §9.1.12.

Administrator action, through the six subprocesses.

## Entity lifecycle

Every entity created by 1.0 carries lifecycle state except the D10 lookups. For all entities with lifecycle state:

- **Creation is immediate.** The entity is active from the moment it is created.
- **No draft state.** No publish step, no approval gate.
- **Deactivation, not deletion.** An entity can be deactivated to remove it from future use. It is never deleted.
- **Edits affect future use only.** No backward propagation to operational records.

D10 lookup values (Outcome State, Assignment Status, Permission Tier, TimeOfDay, ServiceType) do not carry an IsActive flag. They are open lists; retiring a value is a matter of not selecting it in future.

**Source:** System Design Specification §9.1.1, §9.1.12.

## Key rules

### No entity carries a relationship to another at creation

Role carries no reference to Duty. Duty carries no reference to Role. Member carries no list of duties. Branch carries no list of services. Service Definition carries no list of duties (that is a ServiceDefinitionDuty row).

Every relationship is expressed through a join table or a rule table, created by a different process.

**Source:** System Design Specification §2, §9.1.2.

### Names are required but not unique

Two Roles may share a name. Two Duties may share a name. Names are administrator-facing labels.

**Source:** System Design Specification §9.1.2.

### An unreferenced entity is valid

A Duty with no DutyRule and no ServiceDefinitionDuty reference is valid. The system does not warn. 1.2 creates vocabulary; it does not judge whether that vocabulary is useful.

**Source:** System Design Specification §9.1.2.

### Service Schedule carries StartTime

StartTime lives on ServiceSchedule, not on ServiceDefinition and not on BranchTimeSlot. It varies per branch, per slot, and per service simultaneously — ServiceSchedule is the only place all three are fixed.

**Source:** System Design Specification §9.1.5.

### Active schedule uniqueness

An active ServiceSchedule is uniquely identified by the pair (ServiceDefID, TimeSlotID). The uniqueness constraint applies only to active rows. A deactivated schedule does not block creating a new one for the same pair.

**Source:** System Design Specification §9.1.5 (D1 lock).

### OwningBranch enforcement

ServiceDefinition.OwningBranchID is enforced when a ServiceSchedule is created or edited, not when the ServiceDefinition is created. If OwningBranchID is null, any BranchTimeSlot may be used. If set, only matching BranchTimeSlots may be used.

**Source:** System Design Specification §9.1.6.

### Multiple time slots per day are permitted

(BranchID, DayOfWeek) is not unique. A branch may have a Sunday morning slot and a Sunday evening slot.

**Source:** System Design Specification §9.1.3.

### TimeOfDay is descriptive, not a time

TimeOfDayID is a coarse administrator-defined classification. The actual clock time is ServiceSchedule.StartTime.

**Source:** System Design Specification §9.1.3, §9.1.5.

## Invariants

- No configuration process creates a link between Role and Duty except through a DutyRule row written by 2.0.
- Configuration entities are deactivated, not deleted.
- Editing any configuration row affects future use only.
- Created entities are active from creation, where the entity has lifecycle state.
- Names are required but need not be unique.
- Every foreign key references an existing row.
- An active ServiceSchedule is uniquely identified by (ServiceDefID, TimeSlotID).
- ServiceDefinition.OwningBranchID is enforced when a ServiceSchedule is created or edited.
- No configuration process evaluates any rule, threshold, or criterion.

**Source:** System Design Specification §9.3.

---

## What 1.0 does not do

- It does not create Duty Rules. That is 2.0.
- It does not create Members. That is 3.0.
- It does not create Eligibility records. That is 4.0.
- It does not create Events or Programs. That is 8.0.
- It does not evaluate anything.
- It does not invoke any other process.
- It does not read any operational store.

**Source:** System Design Specification §9.2, §9.3.
