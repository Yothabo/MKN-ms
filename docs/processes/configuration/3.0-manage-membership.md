# 3.0 Manage Membership

*Creates and maintains Member records and Identifier History. Derived from the System Design Specification §9. Where this document conflicts with the specification, the specification wins.*

---

## Responsibility

3.0 Manage Membership maintains the member register and the identifier history. It creates and edits Member records, and issues, retires, and reassigns identifiers through the Identifier History log.

It does not assign duties (that is 5.0), does not grant eligibility (that is 4.0), and does not evaluate anything.

**Source:** System Design Specification §9.1.7.

---

## Trigger

Administrator action.

**Source:** System Design Specification §9.2.

## Member record

### Required fields at creation

- JoinDate
- DateOfBirth
- MembershipStage
- Name
- Surname
- Gender
- Phone
- BranchID
- RoleID

Only Email is optional.

**Source:** System Design Specification §9.1.7.

### Cardinality

A Member has exactly one BranchID and exactly one RoleID. There is no MemberRole join table and no MemberBranch join table. A member holds one role and belongs to one branch.

**Source:** System Design Specification §4 (Member).

### MembershipStage

MembershipStage is a free-text field, not a lookup. It is an administrator-defined label stored directly on the Member row.

**Source:** System Design Specification §9.1.7.

### Lifecycle

A Member is created active. Deactivation excludes them from new roster generation without touching any existing operational record. A Member is never deleted.

**Source:** System Design Specification §9.1.1.

### Edits

Changing a Member's BranchID or RoleID affects only future use. Existing operational records (assignments, attendance) retain their historical context, which is anchored to occurrences, not to the member's current attributes.

**Source:** System Design Specification §9.1.7.

## Identifier History

### Purpose

Identifier History is a per-member log of identifier assignments. It tracks every identifier a member has held — its type, its number, when it was assigned, and when (if ever) it was retired.

**Source:** System Design Specification §4 (Identifier History).

### Fields

| Column | Notes |
| --- | --- |
| EntryID | Primary key |
| MemberID | Foreign key → Member |
| Type | Free-text administrator-defined category (e.g., "Card", "Receipt") |
| Number | Administrator-supplied |
| AssignedDate | Required |
| UnassignedDate | Optional. Set on retirement. |
| Reason | Optional |
| AuthorizedBy | Required. Foreign key → Admin. |

**Source:** System Design Specification §4 (Identifier History), §9.1.7.

### Lifecycle

Identifier History has no IsActive flag. Entries are added and retired via UnassignedDate; they are never deleted. The entry is a historical record.

**Source:** System Design Specification §9.1.1, §9.1.7.

### Type

Type is a free-text field. It is not a lookup table. The system manages the assignment/history lifecycle without needing to understand what any given category means.

**Source:** System Design Specification §4 (Identifier History), §9.1.7.

### Number

The Number field is administrator-supplied. The system does not generate identifier numbers.

**Source:** System Design Specification §9.1.7.

### Multiple active identifiers

The system does not prevent two active identifiers of the same Type for one member. If an administrator issues two active cards, both rows exist with UnassignedDate = null. This is a configuration error, not a schema error. The system does not enforce uniqueness beyond the EntryID primary key.

**Source:** System Design Specification §9.1.7.

### Reassignment

Reassignment to a different member is permitted if the administrator chooses. The MKN Configuration Reference sets a default of "identifiers are never reused" — a policy, not a system constraint.

**Source:** System Design Specification §9.1.7.

## Invariants

- A Member references an existing Branch and Role.
- Identifier History references an existing Member.
- Identifier numbers are administrator-supplied, not system-generated.
- Deactivating a Member does not touch operational records.
- Editing a Member does not rewrite operational records.
- Multiple active identifiers of the same type are permitted by the system.
- 3.0 never invokes any other process.
- 3.0 never reads or writes an operational store.

**Source:** System Design Specification §9.3.

---

## What 3.0 does not do

- It does not assign duties.
- It does not grant eligibility.
- It does not create Admin records (that is a separate concern).
- It does not evaluate anything.
- It does not invoke any other process.

**Source:** System Design Specification §9.2, §9.3.
