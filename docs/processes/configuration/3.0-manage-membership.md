# 3.0 Manage Membership

*Creates and maintains Member records and Identifier History. Derived from the System Design Specification §9. Where this document conflicts with the specification, the specification wins.*

---

## Responsibility

3.0 Manage Membership maintains the member register and the identifier history. It creates and edits Member records, and issues, retires, and reassigns identifiers through the Identifier History log.

It does not assign duties (that is 5.0), does not grant eligibility (that is 4.0), and does not evaluate anything.

**Source:** System Design Specification §9.1.7.

---

## Trigger

Administrator action.

**Source:** System Design Specification §9.2.

## Member record

### Required fields at creation

- JoinDate
- DateOfBirth
- MembershipStage
- Name
- Surname
- Gender
- Phone
- BranchID
- RoleID
- MemberStatusID

Optional fields at creation: Email, JoinReason, ReceiptNumber. CardNumber is null until issued.

The member also carries three identifiers. `MemberID` is the system's own primary key, generated by the system, and never changes. `ReceiptNumber` is the congregational identifier held for the first configured duration. `CardNumber` is the congregational identifier issued after the configured duration. Both are administrator-supplied. See the Identifiers section below.

**Source:** System Design Specification §4 (Member), §9.1.7.

### Cardinality

A Member has exactly one BranchID and exactly one RoleID. There is no MemberRole join table and no MemberBranch join table. A member holds one role and belongs to one branch.

**Source:** System Design Specification §4 (Member).

### MembershipStage

MembershipStage is a free-text field, not a lookup. It is an administrator-defined label stored directly on the Member row.

**Source:** System Design Specification §9.1.7.

### Member status

A member's operational state is expressed by `MemberStatusID`, a foreign key to the Member Status entity. The administrator defines the status vocabulary. The seeded defaults for MKN are Active, Inactive, RA, preRA, and Deceased.

Each Member Status carries an `IsRosterable` flag. The roster engine consults this flag to determine whether a member with that status may be assigned to a duty. The system does not interpret any status name; the flag is the mechanical property.

The RA and preRA statuses are defined in the vocabulary but no automated transition moves a member into them. Such transitions belong to a future attendance-driven process, which is not in scope for the current specification. An administrator sets the status directly.

**Source:** System Design Specification §4 (Member Status), §9.1.7.

### Lifecycle

A Member is created with the default Member Status. Deactivation and soft delete exclude the member from new roster generation without touching any existing operational record. A Member is never physically removed. The two-flag lifecycle is stated in Specification §9.6.

**Source:** System Design Specification §9.1.1, §9.6.

### Edits

Changing a Member's BranchID or RoleID affects only future use. Existing operational records (assignments, attendance) retain their historical context, which is anchored to occurrences, not to the member's current attributes.

**Source:** System Design Specification §9.1.7.

### Member attributes

Beyond the fixed columns, a member may carry any number of administrator-defined attributes. The Attribute Type entity holds the vocabulary of attribute names. The Member Attribute Value entity holds one value per member per attribute set, with the date recorded and the admin who recorded it.

Absence of a value means the attribute is not set. The system does not interpret any attribute name or value. Attributes are used by Duty Rules whose criteria type is Member Attribute.

**Source:** System Design Specification §4 (Attribute Type, Member Attribute Value), §5.

### Identifiers

A member carries three identifiers.

| Identifier | Purpose | Admin-supplied | Never reassigned |
| --- | --- | --- | --- |
| MemberID | System identifier. Primary key. | No | N/A — it is the system's own. |
| ReceiptNumber | Congregational identifier held for the first configured duration. | Yes | No — the row is retired when superseded. |
| CardNumber | Congregational identifier issued after the configured duration. | Yes | Yes |

The configured duration is a System Setting named `ReceiptToCardDurationDays`. Its value is a deployment choice; the MKN configuration reference uses 90 days.

The administrator issues a receipt at joining. When the configured duration has elapsed, the administrator issues a card. The receipt's Identifier History entry is marked with an `UnassignedDate` and a `Reason`; the card becomes the current identifier. The receipt is not physically removed; it remains in history.

The system does not detect the threshold or issue identifiers automatically. The administrator issues.

**Source:** System Design Specification §4 (Member), §9.1.7.

## Identifier History

### Purpose

Identifier History is a per-member log of identifier assignments. It tracks every identifier a member has held — its type, its number, when it was assigned, and when (if ever) it was retired.

**Source:** System Design Specification §4 (Identifier History).

### Fields

| Column | Notes |
| --- | --- |
| EntryID | Primary key |
| MemberID | Foreign key → Member |
| Type | Free-text administrator-defined category (e.g., "Card", "Receipt") |
| Number | Administrator-supplied |
| AssignedDate | Required |
| UnassignedDate | Optional. Set on retirement. |
| Reason | Optional |
| AuthorizedBy | Required. Foreign key → Admin. |

**Source:** System Design Specification §4 (Identifier History), §9.1.7.

### Lifecycle

Identifier History carries neither IsActive nor IsDeleted. Entries are added and retired via UnassignedDate; they are never physically removed. The entry is a historical record.

**Source:** System Design Specification §9.1.1, §9.1.7.

### Type

Type is a free-text field. It is not a lookup table. The system manages the assignment/history lifecycle without needing to understand what any given category means.

**Source:** System Design Specification §4 (Identifier History), §9.1.7.

### Number

The Number field is administrator-supplied. The system does not generate identifier numbers.

**Source:** System Design Specification §9.1.7.

### Multiple active identifiers

The system does not prevent two active identifiers of the same Type for one member. If an administrator issues two active cards, both rows exist with UnassignedDate = null. This is a configuration error, not a schema error. The system does not enforce uniqueness beyond the EntryID primary key.

**Source:** System Design Specification §9.1.7.

### Reassignment

Reassignment to a different member is permitted if the administrator chooses. The MKN Configuration Reference sets a default of "identifiers are never reused" — a policy, not a system constraint.

**Source:** System Design Specification §9.1.7.

## Invariants

- A Member references an existing Branch and Role.
- Identifier History references an existing Member.
- Identifier numbers are administrator-supplied, not system-generated.
- Deactivating a Member does not touch operational records.
- Editing a Member does not rewrite operational records.
- Multiple active identifiers of the same type are permitted by the system.
- 3.0 never invokes any other process.
- 3.0 never reads or writes an operational store.

**Source:** System Design Specification §9.3.

---

## What 3.0 does not do

- It does not assign duties.
- It does not grant eligibility.
- It does not create Admin records (that is a separate concern).
- It does not evaluate anything.
- It does not invoke any other process.

**Source:** System Design Specification §9.2, §9.3.
