# 8.0 Manage Events and Programs

*Creates and maintains Events, Programs, Program Items, and Event Duties. Derived from the System Design Specification §9. Where this document conflicts with the specification, the specification wins.*

---

## Responsibility

8.0 Manage Events and Programs maintains the event lifecycle. It creates and edits Events, their Programs, the Program Items within each Program, and the ad-hoc Event Duties on individual items.

It is the only configuration process permitted to create an operational record — and only because a Program Item has been explicitly linked to a Service Definition.

**Source:** System Design Specification §9.1.11.

---

## Trigger

Administrator action.

**Source:** System Design Specification §9.2.

---

## The 8.0 footprint

| Direction | Store |
| --- | --- |
| Reads | D9 (Event, EventBranch, Program, ProgramItem, EventDuty); D3 (ServiceDefinition for ProgramItem.ServiceDefID and EventDuty.ServiceDefID); D4 (Member for EventDuty references); D1 (Duty for EventDuty.DutyID); D10 (AssignmentStatus for EventDuty.AssignmentStatusID) |
| Writes | D9; D3 (event-sourced ServiceOccurrence rows only) |

**Source:** System Design Specification §9.2.

## The 8.0 boundary

8.0 is the sole configuration process permitted to create an operational record. This exception is deliberate and bounded: it applies only when a Program Item is linked to a Service Definition. In that case, 8.0 creates an event-sourced Service Occurrence.

8.0 does not:

- create schedule-sourced occurrences (that is 11.0)
- run the roster engine
- manage the recurring rostering loop
- send notifications
- evaluate fill status

**Source:** System Design Specification §9.0, §9.3.

## Entities maintained

### Event

| Column | Notes |
| --- | --- |
| EventID | Primary key |
| Name |  |
| StartDate |  |
| EndDate |  |
| Type | Free text |
| HostBranchID | Foreign key → Branch. The branch at which the event is held. |

An Event may span multiple days. StartDate and EndDate are both fields. The Event carries no Location field; the host branch expresses where the event is held. A finer physical location, when required, is carried on the Program Item.

**Source:** System Design Specification §4 (Event), §9.1.11.

| Column | Notes |

| EventID | Foreign key → Event. Part of composite primary key. |

The set of branches attending the event. Determines the roster scope across branches. No lifecycle flags; the set is derived from the Event's own state.

### ProgramItem

| Column | Notes |
| --- | --- |
| ItemID | Primary key |

| Title |  |

## Event-sourced occurrence creation

When a Program Item's ServiceDefID is set — at creation or by later edit — the system creates an event-sourced Service Occurrence directly.

The occurrence's values are derived from the **Program Item**, not from a Service Schedule:

| Occurrence column | Derived from |
| --- | --- |
| Date | The date portion of ProgramItem.ScheduledStart |
| StartTime | The time portion of ProgramItem.ScheduledStart |
| ServiceTypeID | The linked ServiceDefinition.ServiceTypeID |
| EventID | The Program Item's Event |
| ScheduleID | null |
| FillStatusID | null |
| GeneratedBy | Administrator |
| CreatedBy | The administrator who created the Program Item |
| ChangedBy | null |

The occurrence's Date and StartTime come from ProgramItem.ScheduledStart. ServiceTypeID is inherited from the linked Service Definition. These are the two separate derivations, and they must not be conflated: the Service Definition supplies the service type, but it does not supply a start time — start time lives on the Program Item in the event case, and on ServiceSchedule in the schedule case.

This occurrence is entirely outside the Occurrence Materializer. It is not subject to 11.0's idempotency, not covered by the (ScheduleID, Date) uniqueness constraint, and not affected by the Materializer's schedule-change or schedule-deactivation rules.

**Source:** System Design Specification §4, §7 (Event-sourced occurrences), §9.1.11.

---

## Comparison with schedule-sourced occurrences

For contrast, a schedule-sourced occurrence (created by 11.0) derives its values from the ServiceSchedule:

| Occurrence column | Schedule-sourced (11.0) | Event-sourced (8.0) |
| --- | --- | --- |
| Date | From the materialized date, per ServiceSchedule's TimeSlot.DayOfWeek | Date portion of ProgramItem.ScheduledStart |
| StartTime | From ServiceSchedule.StartTime | Time portion of ProgramItem.ScheduledStart |
| ServiceTypeID | From ServiceSchedule's ServiceDefinition | From the linked ServiceDefinition |
| EventID | null | The Program Item's Event |
| ScheduleID | The ServiceSchedule | null |
| GeneratedBy | System | Administrator |
| CreatedBy | null | The administrator who created the Program Item |

**Source:** System Design Specification §4, §7.

## Removal of ServiceDefID

If a Program Item's ServiceDefID is removed after an occurrence was created, the occurrence is not automatically deleted. Event-sourced occurrences are governed by 8.0, and cleanup is an administrator action, not a system behavior.

**Source:** System Design Specification §9.1.11.

---

## Lifecycle

Event, Program, ProgramItem, and EventDuty each carry the two-flag lifecycle: IsActive and IsDeleted. Program carries only IsDeleted, because it is one-per-event and deactivated only by deactivating its Event.

Events, Programs, ProgramItems, and EventDuties may be deactivated or soft-deleted; they are never physically removed through normal operations. Deactivation and soft delete do not cascade to event-sourced occurrences.

**Source:** System Design Specification §9.1.1, §9.1.11.

## Invariants

- One Program per Event.
- ProgramItem does not store status; it is computed.
- EventDuty references a real Duty. Eligibility comes from the existing Eligibility and Duty Rule modules.
- EventDuty.ServiceDefID, when set, scopes the duty's per-service rules on that event.
- Event-sourced ServiceOccurrences are created only by 8.0, never by 11.0.
- Event-sourced occurrences have GeneratedBy = Administrator and CreatedBy = the acting admin.
- Event-sourced occurrences derive Date and StartTime from ProgramItem.ScheduledStart.
- Event-sourced occurrences derive ServiceTypeID from the linked ServiceDefinition.
- Deactivation does not cascade and does not touch existing occurrences.
- 8.0 is independent of the recurring roster machinery.
- 8.0 never invokes any other process.

**Source:** System Design Specification §9.3.

---

## What 8.0 does not do

- It does not create schedule-sourced occurrences.
- It does not run the roster engine.
- It does not assign members to configurable duties. Event duties are ad-hoc, not duty-table duties.
- It does not affect the recurring roster loop.
- It does not invoke any other process.

**Source:** System Design Specification §9.2, §9.3.
