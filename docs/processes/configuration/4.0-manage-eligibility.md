# 4.0 Manage Eligibility

*Creates and maintains the Eligibility grant/revoke records that determine duty candidacy. Derived from the System Design Specification §9. Where this document conflicts with the specification, the specification wins.*

---

## Responsibility

4.0 Manage Eligibility creates and manages the binary permission records that determine *candidacy* for a duty. It does not rank candidates — that is 5.2's responsibility — and it does not assign anyone — that is 5.0's responsibility.

Eligibility is the gate. Duty Rule is the ranking. They are independent mechanisms, and 4.0 maintains one of them.

**Source:** System Design Specification §9.1.9.

## Trigger

Administrator action.

**Source:** System Design Specification §9.2.

## The Eligibility record

An Eligibility row represents a single grant/revoke cycle for a (Member, Duty) pair:

| Column | Meaning |
| --- | --- |
| EligibilityID | Primary key — durable identifier |
| MemberID | Foreign key → Member |
| DutyID | Foreign key → Duty |
| GrantedDate | Required |
| GrantedBy | Required. Foreign key → Admin. |
| RevokedDate | Optional. Set on revocation. |
| RevokedReason | Optional |

**Source:** System Design Specification §4 (Eligibility).

---

## Grant and revoke lifecycle

### Grant

A new Eligibility row with GrantedDate set is a grant. The member becomes a candidate for the duty (subject to Duty Rule ranking in 5.0).

### Revoke

Revocation is expressed by setting RevokedDate (and optionally RevokedReason) on an existing row. The row is not deleted.

### Re-grant

A re-grant is a new row. This is why EligibilityID exists as a durable primary key — each grant/revoke cycle is its own row, and the history is preserved.

**Source:** System Design Specification §9.1.9.

---

## Current eligibility resolution

The applicable Eligibility row for a (Member, Duty) pair is determined by:

1. The row whose GrantedDate is in the past.
2. Whose RevokedDate is either null or in the future.
3. If multiple such rows exist, the one with the greatest EligibilityID.

If the resolved row has a RevokedDate in the past, the member is not eligible.

If no row exists at all, the member is not eligible. Eligibility is opt-in — absence is not the same as a grant.

The specific resolution rule is stated in the 5.0 contract, not in the schema. 4.0 does not perform resolution; it stores the records that 5.0 resolves.

**Source:** System Design Specification §9.1.9, §10.

---

## Independence from Duty Rule

Eligibility and Duty Rule are independent. A member can be:

- Eligible for a duty and match every Duty Rule (a strong candidate).
- Eligible for a duty and fail every Duty Rule (falls through to a lower tier or to the no-rules case).
- Ineligible for a duty and match every Duty Rule (never becomes a candidate, because eligibility is the gate).

**Source:** System Design Specification §5, §9.1.9.

---

## Scope

Eligibility is per (Member, Duty). It is not per-branch, per-service, or per-occurrence. If an administrator wants a scoped eligibility, that is expressed through Duty Rule criteria (e.g., ServiceType as a criterion), not through the Eligibility record itself.

**Source:** System Design Specification §9.1.9.

---

## Lifecycle

Eligibility carries neither IsActive nor IsDeleted. Grant/revoke is expressed through GrantedDate and RevokedDate, not through a lifecycle flag. A revoked record stays in the table as history.

**Source:** System Design Specification §9.1.1, §9.1.9.

---

## Invariants

- Eligibility references an existing Member and an existing Duty.
- A grant creates a new row; a revoke sets RevokedDate on an existing row.
- Current eligibility is determined by the latest applicable grant/revoke record.
- Eligibility is independent of Duty Rule.
- 4.0 does not evaluate anything; it stores permission records.
- Revoking eligibility does not touch existing Roster Assignment rows.
- 4.0 never invokes any other process.
- 4.0 never writes to an operational store.

**Source:** System Design Specification §9.3.

---

## What 4.0 does not do

- It does not rank candidates. That is 5.2 (Priority).
- It does not assign members. That is 5.0.
- It does not grant eligibility for all duties at once as a system feature. Each grant is per-duty.
- It does not perform authorization checks. Those are upstream.
- It does not invoke any other process.

**Source:** System Design Specification §9.2, §9.3.
