# 2.0 Configure Duty Rules

*Creates and maintains the Duty Rule rows that express how duties rank candidates. Derived from the System Design Specification §9. Where this document conflicts with the specification, the specification wins.*

---

## Responsibility

2.0 Configure Duty Rules creates, edits, and deactivates Duty Rule rows. A Duty Rule expresses a single criterion, at a single tier, for a single Duty.

This is the process through which an administrator expresses every ranking and filtering relationship between a Duty and whatever criteria the system supports. It is the only mechanism that connects a Role — or Gender, Age, Tenure, or any other criteria type — to a Duty.

2.0 writes rules. It does not evaluate them. Evaluation belongs to 5.0 Generate Assignment.

**Source:** System Design Specification §9.1.10.

---

## Trigger

Administrator action.

**Source:** System Design Specification §9.2.

## Rule shape

A Duty Rule is a row with:

| Column | Meaning |
| --- | --- |
| RuleID | Primary key |
| DutyID | Foreign key → Duty. The duty this rule ranks candidates for. |
| ServiceDefID | Foreign key → Service Definition. Optional. Null means the rule applies to the Duty wherever it appears. Set means the rule applies only where the Duty is required by that Service Definition. |
| TierOrder | Administrator-defined sequence position. |
| CriteriaType | One of the supported criteria types. |
| CriteriaValue | The administrator-entered value for that criterion. |
| IsActive | True at creation. |
| IsDeleted | False at creation. |

**Source:** System Design Specification §4 (Duty Rule), §9.1.10.

---

## The criteria vocabulary

The CriteriaType field is constrained to the fixed vocabulary defined in §5 of the specification:

- Role
- Gender
- Age Range
- Tenure (duration since joining)
- Membership Stage
- Branch-Attendance Recency
- Eligibility Flag
- Member Attribute (references an admin-defined Attribute Type and a required value)
- Youth (computed from DateOfBirth against the configured YouthAgeMin and YouthAgeMax settings)

Plus three reserved types, which may be written but are not evaluated:

- Acceptance Rate
- Duties Carried
- Days Since Last Assignment

These are supported criterion *types*, not rules. Their presence in the vocabulary does not activate them anywhere. Which criteria apply to a given Duty is entirely a matter of administrator configuration.

**Source:** System Design Specification §5.

---

## Rule scope

A Duty Rule may be attached to a Duty alone, or to a Duty in the context of a specific Service Definition.

- **Duty-global rule.** `ServiceDefID` is null. The rule applies to the duty wherever the duty appears, on any service that requires it.
- **Per-service rule.** `ServiceDefID` is set. The rule applies only where the duty is required by that specific Service Definition.

When both kinds of rule exist for the same (Duty, ServiceDefinition) pair, the per-service rules override the duty-global rules entirely for that pair. When only duty-global rules exist, they apply on every service. When only per-service rules exist, they apply on their service and the duty has no rules elsewhere.

Eligibility is not scoped this way. It remains global per (Member, Duty). The per-service refinement is expressed only through Duty Rules.

**Source:** System Design Specification §4 (Duty Rule), §10.1.5.

---

## Tier composition

Multiple rules may share the same TierOrder for a single Duty. Rows sharing a TierOrder are ANDed — all of them must be satisfied for a member to match that tier.

No OR operator is provided within a tier. Tiers themselves express ordered-preference OR: the engine tries Tier 1, and only if it produces no candidate does it fall through to Tier 2.

No NOT operator is provided. It is a non-breaking addition to make later if a genuine need appears.

**Source:** System Design Specification §5, §9.1.10.

---

## Tier ordering

TierOrder is an administrator-defined sequence position. Its values are integers. Gaps are permitted — an administrator may leave Tier 2 empty and use Tier 3.

TierOrder does not imply any behavior beyond its position in the ascending sequence.

**Source:** System Design Specification §9.1.10.

---

## CriteriaValue

CriteriaValue is a free-text field in storage. Its interpretation depends on CriteriaType:

- For CriteriaType = Role: the value names a Role.
- For CriteriaType = Age Range: the value is a range (e.g., "13-35").
- For CriteriaType = Gender: the value names a gender.
- And so on.

The system does not validate CriteriaValue at write time. Validation belongs to whichever process evaluates the rule (5.0). A rule with a CriteriaValue that does not match any configured entity simply never matches a member.

**Source:** System Design Specification §9.1.10.

---

## Editing and deactivation

A Duty Rule is editable. Changes to TierOrder, CriteriaType, or CriteriaValue take effect on the next 5.0 run. Existing Roster Assignment rows are not rewritten — the no-backward-propagation rule applies.

A Duty Rule is deactivated, never deleted. A deactivated rule is invisible to 5.0's evaluation.

**Source:** System Design Specification §9.1.1, §9.1.10.

---

## Invariants

- A Duty Rule references an existing Duty.
- Multiple rules may share TierOrder for a single Duty. Same-tier rules are ANDed.
- TierOrder gaps are permitted.
- A deactivated rule is invisible to 5.0. A soft-deleted rule is invisible everywhere.
- Editing a rule does not rewrite any operational record.
- Per-service rules override duty-global rules entirely for that (Duty, ServiceDefinition) pair.
- 2.0 never evaluates a rule; it only stores one.
- The CriteriaType vocabulary is fixed at write time. An administrator cannot invent a new criteria type without a specification revision.

**Source:** System Design Specification §9.3.

---

## What 2.0 does not do

- It does not evaluate any rule.
- It does not link Role to Duty. A Duty Rule describes a preference; the system reads it as data.
- It does not create Duties. That is 1.0.
- It does not create Eligibility records. That is 4.0.
- It does not invoke any other process.

**Source:** System Design Specification §2, §9.3.

---

## Example shape

Three Duty Rules for a single Duty, expressing "Tier 1: Role = Messenger":

| RuleID | DutyID | TierOrder | CriteriaType | CriteriaValue |
| --- | --- | --- | --- | --- |
| 1 | 5 | 1 | Role | Messenger |

A Duty with no rules configured falls into the "no rules" case: every eligible member enters as an equal candidate.

A Duty with two tiers, where Tier 2 is "any eligible member," is expressed as a single rule at Tier 2 with CriteriaType that always matches, or as no further tiers (the engine falls through and every remaining eligible member is a candidate).

**Source:** System Design Specification §5, §9.1.10.
